# refine-issue

## 概要

GitHub issue を起点に、内容を深掘り・詳細化して **issue 本文(body) そのものを更新する** ワークフロー・スキル。
issue の **種別（PBI / サブタスク / 技術タスク）を判定**し、種別ごとの本文構造で全置換する。
**PBI の場合は、深掘り後にサブタスクへの分割を提案し、同意のうえ gh でサブタスク issue を起票する**。
次の流れをオーケストレーションする: issue 取得（gh）→ 種別判定（ラベル / 無ければ質問して付与）→
現状の詳細度を評価 →（十分なら確認の上スキップ可）→ 要件を深掘り（brainstorming）→
種別テンプレで本文ドラフト → 同意ゲート（AskUserQuestion）→ gh で本文を全置換（画像・添付は保全）→
（PBI のみ）サブタスク分割の提案 → 同意ゲート → gh でサブタスク issue 起票（Project 継承・sub-issue 関連付け）。
`issue-to-pr` が ADR・実装計画を `docs/` に作り実装・PR まで進めるのに対し、本スキルは **issue 自体**（と配下サブタスク）を充実させる。

## 種別と本文構造

種別は `PBI` / `subtask` / `tech` ラベルで判定する。**ラベルが無ければ AskUserQuestion で種別を確認し、確定後に種別ラベルを付与する**（`gh issue edit --add-label`）。

本文の見出しは **Issue Forms が生成する `### <ラベル名>` と一致させる**（フォーム作成と手動詳細化で構造がブレないように）。

| 種別       | ラベル    | 本文構造（`###` 見出し）                                                                                                                                                     |
| ---------- | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PBI        | `PBI`     | ユーザーストーリー / 何を・なぜ（What・Why） / 受け入れ条件（**ユーザー目線・技術観点NG**）                                                                                  |
| サブタスク | `subtask` | 親PBI（`#N` 参照） / 概要 / 実装方針（How）（基本〜詳細設計） / 満たす親PBIの受け入れ条件（**番号参照・本文コピー禁止**） / 依存関係（Blocked by / Blocks を `#N` リンクで） |
| 技術タスク | `tech`    | 何を・なぜ（What・Why） / 実装方針（How） / 受け入れ条件（**技術観点OK**）                                                                                                   |

- **サブタスクのタイトルは `[T<n>] <要約>`**（例: `[T1] セッション保存APIを実装する`）。
  T 番号は **PBI ごとに採番**する（その PBI 配下で T1..Tn。PBI が変われば T1 に戻る）。
- **依存関係**は Blocked by（自分が待つ先行タスク）/ Blocks（自分を待つ後続タスク）の2リストに分け、
  相手サブタスクを **`#N` 実リンク**で書く（クリック可能・被参照側に自動バックリンク。別PBIのサブタスクも参照可）。
  同じ1本の依存は両端に二重記載になるが、起票時に refine-issue が DAG から整合させる。

## いつ使うか

- issue の記述が曖昧・浅く、実装に入る前に内容を詳細化したいとき
- PBI を具体的な作業（サブタスク）に分割したいとき
- 使わない場面:
  - 既に十分詳細な issue（その場合は本スキルが Step 2 で確認の上スキップする）
  - 設計判断(ADR)・実装計画・実装が目的なとき → `issue-to-pr`
  - コードを書く段階 → `tdd-implement`

## 前提・入力

- **gh CLI が認証済み**であること（`gh auth status`）。対象 issue に書き込み権限が必要。
- **引数**: issue の URL（または番号）。未指定なら対象を確認する。
- 既定 UI コピーは日本語（`CLAUDE.md`）。**詳細化後の本文も日本語**で書く。
- 本スキルは **ローカルファイルを書かない / コミットしない**。成果物は GitHub 上の変更のみ:
  対象 issue の **body**、種別ラベルの付与、**（PBI のみ）新規サブタスク issue の起票・
  Project への追加・親PBIへの sub-issue 関連付け**。

## パイプライン上の位置

- 処理順序は **refine-issue（分割・詳細化）→ issue-to-pr（計画→実装→PR）**。
  PBI は本スキルでサブタスクに割ってから、各 subtask/技術タスクを `issue-to-pr` にかける。
- サブタスクの起票では、Forms（`.github/ISSUE_TEMPLATE/2-pbi-subtask.yml`）と同じ
  `### 親PBI / ### 概要 / ### 実装方針（How） / ### 満たす親PBIの受け入れ条件 / ### 依存関係` 構造を本文に再現し、
  タイトルを `[T<n>] <要約>`、`subtask` ラベルと親 PBI への `#N` 参照を必ず付ける
  （CLI 起票は Forms を通らないため自前で揃える）。
- 依存（`#N` リンク）は起票前に番号が無いため、起票を**複数パスに分ける**
  （Project 継承 → 番号・node ID 回収 → sub-issue 関連付け → 依存解決。Step 6）。

## ワークフロー

各ステップを TodoWrite でタスク化し、順番に実行する。

### Step 1 — Issue を取得して種別を判定する

- `gh issue view <番号|URL> --json number,title,body,labels,url,author,state --comments`
  で取得する（コメントも要件の手がかり）。
- `labels` から種別（`PBI` / `subtask` / `tech`）を判定する。
- **種別ラベルが無ければ AskUserQuestion で種別を確認し、確定後に
  `gh issue edit <番号|URL> --add-label <種別>` で付与する。**
- 「種別に対応する本文構造」（上表）に照らして **現状の詳細度を評価** し、不足している観点を洗い出す。
- 現状の要約と「埋めるべき空白」をユーザーに提示し、認識を合わせる。

### Step 2 — 十分に詳細なら確認の上スキップする（早期ゲート）

- 既に実装に着手できる詳細度だと判断したら、**AskUserQuestion** で
  「詳細化は不要としてスキップ」/「それでも深掘りする」を確認する。
  （PBI でサブタスク分割が未了なら、スキップ時も Step 6 の分割提案だけは案内してよい。）
- スキップが選ばれたら、その旨を伝えて終了する（**issue は変更しない**）。
- 深掘りが選ばれたら Step 3 へ進む。
- 詳細度が不十分なら、この確認は省いて Step 3 へ進んでよい。

### Step 3 — 内容を深掘りする（brainstorming）

- **REQUIRED SUB-SKILL: superpowers:brainstorming を使う。**
- Step 1 で洗い出した空白を中心に、1 問ずつ徹底的に壁打ちする。**種別に応じて観点を変える**:
  - **PBI**: ユーザーストーリーの完形（誰が・何を・なぜ）/ What・Why（背景・スコープ・対象外）/
    受け入れ条件（**ユーザー目線・技術観点を入れない**・正常/異常/境界）。
  - **サブタスク**: 概要 / 実装方針（How＝基本〜詳細設計）/ 満たす親PBIのAC（番号参照）。
    親PBIの内容も `gh issue view <親番号>` で参照して整合を取る。
  - **技術タスク**: What・Why / 実装方針（How）/ 受け入れ条件（**技術観点OK**・性能・セキュリティ・互換性・運用 など）。
- **brainstorming の既定を上書きする:**
  - 設計成果物を `docs/superpowers/specs/...` に保存しない。成果物は **issue 本文**（Step 4–5）と **サブタスク issue**（Step 6）。
  - 自動コミットしない（このスキルはローカルファイルを書かない）。
  - 合意は会話だけで済ませず、Step 5 / Step 6 の AskUserQuestion ゲートで取る。
  - 終端で **writing-plans に遷移しない**（本スキルの終端は issue 更新）。

### Step 4 — 種別テンプレで本文ドラフトを作る

- 深掘り結果を**種別の本文構造**（「種別と本文構造」表、`###` 見出し）にまとめる。該当しない見出しは省く。
- Forms が生成する見出しと一致させる。例（PBI）:

  ```markdown
  ### ユーザーストーリー

  （ログイン中のユーザー）として、…したい。なぜなら…だから。

  ### 何を・なぜ（What・Why）

  …

  ### 受け入れ条件

  - [ ] …
  ```

- 元の本文にあった有用な情報は **取りこぼさず** ドラフトへ取り込む（全置換でも情報を失わない）。
- ドラフトをユーザーに提示してレビューを受け、必要なら修正する。

### Step 5 — Issue 本文を更新する（AskUserQuestion で同意）

- **画像・添付を保全する（全置換で失う前に）。** 元 body から次の3種を抽出し、新 body（Step 4 のドラフト）に
  取り込まれているか確認する。漏れていれば取り込む。**全置換は body を丸ごと差し替えるため、ここで拾わないと不可逆に失う:**
  - Markdown 画像 `![alt](url)`
  - HTML `<img ... src="…">`
  - user-attachments / githubusercontent への添付リンク `[label](url)`（動画・PDF・zip 等）

  テンプレの見出しに自然に収まらなければ、末尾に `### 参考資料（元 issue から保全）` を設けて再掲する。
  **保全対象が無ければ何も足さない。**

- **HARD GATE: gh で更新する前に、AskUserQuestion で「この本文で issue を更新してよいか」の同意を必ず取る。**
- 同意後に **のみ** 本文を全置換する。クォート付きヒアドキュメントで渡す（`$`・バッククォートの展開を防ぐ）:

  ```bash
  gh issue edit <番号|URL> --body-file - <<'EOF'
  ### ユーザーストーリー
  …（ドラフト全文）…
  EOF
  ```

  - **body** を全置換する（種別ラベルは Step 1 で確定済み。`--add-label` は種別確定時のみ使う）。
  - 元の本文は GitHub の編集履歴に残るため復元可能（全置換戦略の前提）。

- 更新後、`gh issue view <番号|URL> --json url,title,updatedAt` 等で反映を確認する。
- **種別が PBI なら Step 6 へ。それ以外はここで完了**（URL を添えて報告）。

### Step 6 —（PBI のみ）サブタスクへ分割して起票する（AskUserQuestion で同意）

- 深掘りで見えた作業を、独立して着手できる**サブタスク**に割る。各サブタスクに
  概要 / 実装方針（How）/ 満たす親PBIのAC（番号参照）/ 依存関係 を用意する。
- **T 番号を採番する**: PBI ごとに `T1..Tn`。**既存サブタスクがある PBI なら**、配下サブタスク
  （`gh issue list --label subtask --search "<親番号>"`）のタイトルから `[T<数>]` の最大値を読み、続きから採番する。
- **依存の DAG を確定する**: サブタスク間の Blocked by / Blocks を決める（循環が無いか確認）。
- 分割案（`[T<n>]` 付きの一覧・各本文ドラフト・依存関係）をユーザーに提示する。
- **HARD GATE: 起票する前に、AskUserQuestion で「この分割で起票してよいか」の同意を必ず取る。**
- 同意後に **のみ**、**多パス**で起票する（依存の `#N`・Project 継承・sub-issue 関連付けを順に解決）。
  各パスの詳細コマンドは [references/subtask-creation.md](references/subtask-creation.md) を参照:

  **パス0 — 親PBIの Project と node ID を取得する。** 親の `projectItems` から継承先 Project を得る
  （取得不可・未所属なら既定 Project ＝ subtask-creation.md の定数）。親の node ID も控える。

  **パス1 — 全サブタスクを起票して番号・node ID を回収する。** 依存関係は一旦 `[T<n>]` エイリアスで書いておく。
  起票時に継承（無ければ既定）Project へ `--project` で載せる。`T<n> → #<番号>` の対応表を作る。

  **パス1.5 — 親PBIの sub-issue として関連付ける。** 親と各子の node ID で `addSubIssue` を実行する
  （gh ネイティブ無し → GraphQL）。

  **パス2 — 依存を実リンクに解決する。** 対応表で `[T<n>]` を `#<番号>` に置換し、各サブタスクの
  body を `gh issue edit <番号> --body-file - <<'EOF' … EOF` で更新する（Blocked by / Blocks 両方向を整合させる）。
  依存が無いサブタスクは依存関係を空のままにしてよい。

  **Project 追加・sub-issue 関連付けが失敗したら握りつぶさず報告**し、手動手順を案内する
  （`gh project item-add` / GitHub UI の "Create sub-issue"）。

- 起票・解決した各サブタスク（`[T<n>] #<番号>` と URL）を親 PBI に紐づけて報告する。
  必要なら親 PBI 本文末尾に `- [T1] #123 要約` 形式のサブタスク一覧を追記してよい
  （`issue-to-pr` のサブタスク扱いにも効く）。
